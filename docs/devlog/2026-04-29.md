### 発端

ユーザー観測: 2026-04-26 以降の本番ラン全機種で `rakutenMin: null`、`rakutenAvg: null`。Yahoo! は機能している。

### 一次調査と誤診（要反省）

最初の診断は「`RAKUTEN_APP_ID` 自体が無効」と書いたが、これは表層症状に過ぎなかった。ユーザーから「楽天 Developer サイト上の各キーは 30 文字程度（20 桁数字ではない）」「2026-02-10 に API 移行のプレスリリースがある」との指摘で再調査。

### 一次情報（公式・ブログ複数）の突き合わせ

| 軸 | 旧 | 新 |

### ライブ検証（curl）

1. 旧 endpoint に現 `RAKUTEN_APP_ID` (UUID) を渡す → `400 specify valid applicationId`（旧は 20 桁数字を期待するため UUID を弾く）
2. 新 endpoint に同 `RAKUTEN_APP_ID` を渡す → `400 accessKey must be present as a query parameter or in the header`（applicationId 自体は通過、accessKey 不足のみ）

→ ユーザーは Developer Dashboard で新仕様アプリ登録までは済ませており、`.dev.vars` の applicationId は新仕様の有効値。コードが旧 API のままだったため 100% null になっていた構図。タイムリミットは 2026-05-13（あと 14 日）。

### Yahoo! 側の確認

Yahoo! ショッピング v3 API はリプレース告知なし、文言修正と sandbox 終了のみ。本プロジェクトでの移行は不要。

### 学び

- silent failure の害: `if (!response.ok) return null` が認証失敗を 2 ヶ月以上隠した。今後は 4xx に最低限の `console.warn` を残す（本 PR で実装済）
- 表層症状で診断を打ち切らない: 「APP_ID が無効」を結論にする前に、API 自体の状態を確認すべきだった。ユーザーが「形式が違う」「移行告知がある」と指摘してくれて初めて根本に到達した
- 廃止予定 API への迂回は割に合わない: 旧仕様は 14 日後に停止、二系統併存はメンテ負債。一括切替を選択
